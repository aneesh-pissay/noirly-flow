# Security deployment notes

## Comment mentions

Task comments now accept explicit member selections from the `@` picker. The server validates mention ranges and workspace membership; raw typed names or email addresses do not create notifications. Comments retain selected user IDs and text ranges for highlighting. Each selected user is queued once per comment, including self-mentions. Editing a selected name removes that selection rather than silently tagging a different person.

Mail jobs are embedded in the comment document and claimed with a five-minute lease. Delivery rechecks that the recipient still belongs to the workspace and the task exists. The initial worker runs after the POST response; failures remain queued with backoff. `vercel.json` schedules `/api/cron/comment-mentions` daily at 00:00 UTC for retries. Supply a random `CRON_SECRET` of at least 32 characters in the Flow Vercel project so scheduled calls authenticate. The endpoint accepts `Authorization: Bearer <CRON_SECRET>`. More frequent retries require a compatible scheduler configuration. A process failure after SMTP accepts mail but before MongoDB records success can produce a duplicate on retry; this is at-least-once delivery.

Configure Flow's `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASS`, `EMAIL_FROM`, and production `NEXT_PUBLIC_APP_URL`/`AUTH_URL`. Missing SMTP leaves jobs pending, not marked sent. `MENTION_EMAIL_OUTBOX` is a local-only preview directory; leave it unset in production. Browser-test configuration uses an isolated outbox. No live email was sent while implementing this feature; tests and deployment have not been run for this change.

## Task assignment and overdue emails

Task completion also queues an email to the task creator (the current task-owner equivalent) and every assigned member, deduplicated by user ID. The recipient jobs persist in the same write that changes the status to `done`, for task edits and board moves; creating a task already marked done also queues them. Ordinary edits to a completed task do not resend mail. Reopening clears pending completion jobs, and completing again creates a fresh event. Delivery rechecks that the task is still done, exists, and the recipient still belongs to the workspace and is its creator or an assignee. It uses the same task worker, SMTP settings, outbox, lease, retry schedule and delivery limits below. No separate credentials or cron entry are required. Completion emails have not been tested or deployed, and no live emails were sent during implementation.

New task assignments are durably queued in the same task write. Each newly assigned member receives an assignment email; retained assignees are not notified again on ordinary edits. Removing and later reassigning a member creates a new delivery. Recurring task occurrences also queue assignment mail. The create, edit and board-move endpoints start an assignment worker after returning their response.

`vercel.json` schedules `/api/cron/task-emails` at 03:30 UTC (09:00 Asia/Kolkata) daily. It retries pending assignment mail and sends one overdue reminder per task and assignee per India calendar day, starting the day after the due date. Existing tasks participate automatically, without historical assignment emails. Tasks without due dates receive no overdue reminders. Completion, cancellation, deletion, unassignment, or removal from the workspace stops subsequent notifications. Changing a due date is checked before delivery. Emails already accepted by SMTP cannot be recalled.

Both email workers use the same Flow SMTP configuration and `CRON_SECRET` described above. Set `TASK_EMAIL_OUTBOX` only for local previews; it writes JSON files instead of sending mail. The browser test environment sets an isolated task outbox. Deployment and live mail verification were not performed, and no tests were run for this feature.

Delivery uses a five-minute claim lease and retry backoff. Success is recorded only after SMTP accepts the message. SMTP delivery is at least once: a crash after acceptance can cause a duplicate. A worker invocation is bounded to 50 attempts / about 35 seconds of work plus the current mail operation. The response includes `more` when that budget is exhausted. For volumes exceeding one daily invocation, configure a scheduler/queue to drain repeated authenticated calls and monitor deferred mail; the provided daily schedule alone does not guarantee every recipient is processed that day. Vercel invocation timing and SMTP acceptance do not guarantee exact inbox arrival time.

## Direct R2 attachment uploads

When all four `R2_*` settings are present, Flow issues a five-minute, content-type-bound PUT URL and the browser uploads bytes directly to R2. Flow verifies object size and content, copies validated files from `flow/attachment-uploads/` to the private `flow/attachments/` prefix, then records attachment metadata. Without R2 configuration, local development keeps using the existing Flow upload route. Downloads still pass through Flow's authorization-checked API. Create a bucket-scoped R2 API token with Object Read & Write access. In the R2 bucket's CORS policy, allow `PUT`, `Content-Type`, and the exact Flow origin (plus any origins used for local or preview uploads). Add a lifecycle rule expiring the `flow/attachment-uploads/` prefix after one day to clean up uploads that never get finalized. Do not make the bucket public. The R2 values are listed in `.env.example`; no public bucket URL is needed.

## Coordinated rollout

The coordinated rollout guide is maintained in the sibling Identity repository at `docs/SECURITY-ROLLOUT.md`.

Deploy Identity before this Flow update and the mobile release. Configure strong production secrets and a trusted ingress header for shared rate limiting. Cookie-authenticated custom API mutations must send `X-Noirly-CSRF: 1` and originate from the same origin; the API client supplies this header. Native bearer requests use their own authentication path.

MongoDB tenant isolation is enforced in server queries and permissions, not database RLS. Task attachments now use bounded multipart reads, a 25 MB file cap, byte checks for inline MIME types, safe download headers and workspace authorization. Files are not malware-scanned. Production browser source maps are disabled; review previously uploaded CDN assets separately.

The full dependency audit reports five development-tooling findings through unpatched `braces`; the production-only audit reported zero. The current unit suite passes 63 tests and full lint passes. On 13 October 2026, the production build and all 15 selected browser authentication, attachment, CSRF, CSP and source-map checks passed against a disposable database and local storage. The later full browser run had 59 passes and four unresolved failures: CSV export, chat updates, email invite acceptance and the already-a-member invite message. E2E configuration clears R2 credentials to prevent inheritance from local production configuration. Flow JWT authentication and authorized event delivery passed against an isolated realtime server; a cross-project subscription was denied. No production deployment was performed. Vercel configuration and its upload/realtime limits are documented in the sibling Identity repository's `docs/VERCEL-CONFIGURATION.md`.
